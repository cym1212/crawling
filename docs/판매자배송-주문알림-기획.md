# 판매자배송 주문 알림 + 출고 연동 — 기획 문서 (확정본)

> 상태: **기획 확정** (2026-08-24) — 슬랙 다이제스트 템플릿 시안만 채팅 확정 후 구현 시작.
> 미출고 리마인드(Level 3의 재알림)는 전체 구현 후 별도 논의.

---

## 1. 목적

판매자배송(마켓플레이스) 주문은 판매자가 직접 출고해야 하는데, 현재는 Wing 접속/메일로만 인지 가능하다.
→ **주문을 자동 감지해 슬랙으로 모아 알려주고, 출고 처리(송장 발급→쿠팡 등록)를 30-we.com 화면에서 버튼으로 처리**한다.

## 2. 확정된 설계

### 2-1. 알림 (crawling 담당)

| 항목 | 확정 내용 |
|---|---|
| 방식 | 실시간 폴링 ❌ → **다이제스트**: 하루 2회 정해진 시각에 모아서 발송 |
| 발송 시각 | **09:00, 12:00** (yml로 조정 가능하게) |
| 대상 | 아직 알림 안 된 신규 결제완료 주문 전부 (주문번호 기록으로 중복 방지) |
| 0건일 때 | 발송 안 함 (기본값, 조정 가능) |
| 채널 | **새 슬랙 채널** (웹훅 별도 발급 — 부족재고 채널과 분리) |
| 내용 | 상품명+옵션 / 수량 / 결제시각 / 주문번호 + 건수 요약. **수취인 개인정보는 슬랙에 넣지 않음** (30-we 화면에서만) |
| 형식 | Block Kit 카드 (부족재고 알림과 동일한 스타일, 가독성 우선) — 시안 채팅 확정 후 구현 |

### 2-2. 출고 처리 (30-we.com 화면 + 버튼 2개)

**버튼을 분리한다** — 로젠 송장은 내부 작업이라 재발급이 자유롭지만, 쿠팡 등록은 고객에게 노출되어 수습이 어려우므로 사이에 사람 검수를 둔다:

```
[버튼 A: 송장 발급]  로젠 발급 + 라벨 인쇄까지만 (쿠팡 안 건드림, 재발급 자유)
        ↓  사람 검수 (라벨의 수취인·주소·상품 확인)
[버튼 B: 쿠팡 등록]  쿠팡 준비중 처리 → 송장번호 등록 (순차 자동) ← 유일한 확정 지점
```

- 준비중 처리를 B에 묶는 이유: 쿠팡 규칙상 송장 업로드는 "상품준비중" 상태에서만 가능 + 준비중부터 고객 취소가 제한되므로 사람 확인 후 영역에 둔다.
- B는 30-we.com이 **crawling 내부 API를 호출**하는 방식 (쿠팡 API 키는 crawling만 보유 원칙 유지).

### 2-3. 작업자 플로우 (완성 후)

```
① 09시/12시 슬랙 다이제스트 확인
② 30-we.com 쿠팡 주문 화면 → 신규 주문 목록 (수취인 상세 포함)
③ 창고 재고 확인
④ [송장 발급] → 라벨 인쇄 → 검수 (틀리면 재발급)
⑤ [쿠팡 등록] → 준비중+송장 자동 등록
⑥ 포장 · 라벨 부착 · 로젠 발송  → 이후 배송 추적은 쿠팡 자동
```
사라지는 일: Wing 로그인, 주문 찾기, 준비중 클릭, 송장번호 타이핑.

## 3. 근거 사실 (공식 문서·코드 검토 결과)

### 3-1. 쿠팡 API 지원 현황

| 작업 | API | 확인 내용 |
|---|---|---|
| 주문 조회 | 발주서 목록 조회 (분단위/일단위) | 상태별 조회, 분단위는 24시간 창 |
| 준비중 처리 | ordersheets/acknowledgement (PATCH) | 결제완료→상품준비중, 박스 단위 최대 50건 일괄 |
| 송장 등록 | 송장업로드 API | 준비중 상태에서만 가능, 등록 시 자동으로 배송지시 전환. 택배사 코드 목록 API 제공(로젠 포함) |
| 송장 수정 | 송장업데이트 API | 잘못 등록한 송장 교체 |
| 이후 상태 | (API 불필요) | 배송중/배송완료는 쿠팡이 택배사 추적으로 자동 갱신 |

수동 작업은 정확히 2개(준비중, 송장 입력)이며 **둘 다 API로 대체 가능**.

### 3-2. 주문 API가 주는 구매자 정보 (Wing 화면과 동일 수준)

- 주문자: 이름(마스킹됨, 예: "신*희"), 연락처는 **안심번호**만 (실번호 null), 이메일 미사용
- 수취인: 이름, 안심번호, **전체 주소**(addr1/addr2/우편번호), 배송요청사항
- 상품: 노출상품명/등록상품명/옵션명, 수량, 개당가/결제금액/할인, 출고예정일
- → **로젠 발급에 필요한 데이터(이름·안심번호·주소)가 전부 옴.** 안심번호는 택배 발송용 표준.

### 3-3. 30-we.com 로젠 연동 현황 (코드 검토)

- ✅ 완동 중: `LogenApi` 서비스(송장번호 실시간 발급·주문정보 등록·출력확인), 감열지 라벨 인쇄(바코드 포함), 일괄 발급, 재발급
- ❌ 한계: 발급 로직이 거래명세서(TradeSupply)에 강결합 — "수취인+상품 → 송장번호" 독립 서비스 없음, 발신인 하드코딩
- → 30-we.com 쪽에 **발급 로직 서비스 추출 리팩토링** 필요 (의뢰 #3 영풍문고 자동화에도 동일하게 필요한 작업이라 공용)

## 4. 역할 분담과 개발 순서

| 순서 | 담당 | 작업 |
|---|---|---|
| 1 | crawling | 주문 수집→공유 DB 적재(수취인 포함, 스키마=의뢰서 계약), 다이제스트 슬랙(09/12시), 내부 API 2개(준비중 처리·송장 업로드) |
| 2 | crawling→사용자 | 의뢰서 #5 작성(코드 레벨)·전달: 주문 화면 + 버튼 A/B, 로젠 서비스 추출 |
| 3 | 30-we 개발자 | 리팩토링 + 화면/버튼 구현 (로젠 추출은 1과 병렬 가능) |
| 4 | 공동 | 통합 테스트 — 실제 판매자배송 주문 1건으로 end-to-end (준비중/송장 API는 실주문에만 동작) |

## 5. 데이터 저장 (crawling, Level 2)

- 주문 테이블: 주문번호, 결제일시, 상태, 수취인(이름/안심번호/주소/요청사항), 상품별(옵션ID/상품명/수량/금액), 알림 발송 여부, 출고 처리 상태
- 개인정보 최소화: 안심번호·마스킹명만 저장 (쿠팡이 실정보를 안 주므로 자연 충족). 상세 스키마는 구현 승인 시 확정해 의뢰서에 계약으로 명시.
