# 30-we.com 기능 개발 의뢰서

> crawling 프로젝트에서 생산하는 데이터를 30-we.com에서 조회/표시하기 위한 기능 개발 요청 문서.
> 새 기능이 생길 때마다 이 문서에 의뢰 항목을 추가하고, 준비가 되면 한꺼번에 전달한다.
> **의뢰 상세의 코드는 30-we.com의 기존 컨벤션(Bsight 모듈)을 그대로 따라 작성했으므로, 그대로 구현하면 된다.**

---

## 1. 공통 전제 (모든 의뢰에 적용)

### 1.1 두 프로젝트의 역할

| 프로젝트 | 역할 |
|---|---|
| **crawling** (Spring Boot, :8081) | 데이터 생산: 쿠팡 API 연동, 스케줄 수집, 부족 재고 계산, 슬랙 알림, DB 적재 |
| **30-we.com** (Laravel 8, PHP 7.3) | 데이터 소비: crawling이 만든 데이터를 **조회해서 화면에 표시** (읽기 전용) |

- 30-we.com에서는 **쓰기 작업이 없다.** 입고 신청 실행 등 액션성 기능은 전부 crawling 쪽에서 처리한다.
- 30-we.com은 쿠팡 API 키, HMAC 인증, 호출 제한을 전혀 알 필요 없다.
- 테이블은 crawling의 JPA가 자동 생성/관리하므로 **30-we.com에서 마이그레이션을 만들지 않는다.** 모델만 작성한다.

### 1.2 DB 커넥션

crawling이 적재하는 테이블은 AWS RDS의 `bsight` DB에 있다. 30-we.com의 `config/database.php:86-98`에 이미 정의된 `mysql_bsight` 커넥션을 사용한다.

- 모델에 `protected $connection = 'mysql_bsight';`를 명시한다.
- `.env`의 `DB_HOST_BSIGHT` / `DB_DATABASE_BSIGHT`(=bsight) / `DB_USERNAME_BSIGHT` / `DB_PASSWORD_BSIGHT`가 crawling이 쓰는 RDS를 가리키는지 확인 필요. 접속 정보는 이 문서에 적지 않고 별도 전달한다.

### 1.3 데이터 연동 방식 (2가지 패턴)

**패턴 A — DB 직접 조회 (기본):** crawling 스케줄러가 주기 수집해 적재한 테이블을 read-only 모델로 조회. 목록/검색/이력 화면은 전부 이 방식.

**패턴 B — 실시간 내부 API 호출:** "지금 새로고침" 같은 진짜 실시간 값이 필요할 때만, 30-we.com 서버가 crawling의 내부 API를 HTTP 동기 호출한다. crawling이 그 자리에서 쿠팡 API를 호출해 JSON을 즉시 반환하며, 조회 결과는 부수적으로 DB 스냅샷에도 반영된다 (→ 새로고침 후에는 패턴 A의 목록/마지막 동기화 시각도 최신이 됨).

- 인증: 요청 헤더 `X-Internal-Token: {토큰}` (토큰 값은 별도 전달, `.env`에 보관)
- crawling 서버 장애/타임아웃 시 이 호출만 실패 → 화면은 패턴 A의 마지막 동기화 데이터로 폴백

### 1.4 30-we.com에 추가할 공통 설정

`config/services.php`에 추가 (기존 `taskboard_webhook` 항목과 같은 방식):

```php
'crawling' => [
    'base_url' => env('CRAWLING_BASE_URL', 'http://127.0.0.1:8081'),
    'internal_token' => env('CRAWLING_INTERNAL_TOKEN', ''),
],
```

`.env`에 추가 (실제 값은 별도 전달):

```
CRAWLING_BASE_URL=http://{crawling서버주소}:8081
CRAWLING_INTERNAL_TOKEN={별도전달}
```

| 7 | 위탁 거래처 발주 자동 수신 + AI 거래명세서 작성 (업무폰 알림 → 발주 수신함 → 항목별 Enter 확정) | 자체 (안드로이드 수신기 앱 + 30-we, **crawling 무관**) | 확정 (일부 결정 필요 — §7-11) |
| 8 | 쿠팡 로켓그로스 입고 신청 자동화 (신청 화면 → WING RPA 제출 → 로젠 송장 자동 발급 → 입고 추적) | 패턴 A + 내부 API + RPA 에이전트 (**예외: 30-we가 액션까지 수행**) | 확정 — crawling 구현·배포 완료, **30-we 작업 시작 가능** |

상태 정의: `초안`(스키마 미확정) → `확정`(스키마/코드 확정, crawling 구현 대기) → `전달됨`(작업 시작 가능) → `완료`

> **⚠️ 의뢰 #3은 예외 유형입니다.** 의뢰 #1·#2는 "crawling이 만든 데이터를 30-we가 조회만"(읽기 전용)이지만, **의뢰 #3은 30-we가 이미 보유한 Trade(거래명세서·로젠송장·팝빌문자·재고) 기능을 사용해야 하므로 30-we가 쓰기·액션까지 수행**합니다. 공통 전제(§1)의 "30-we는 읽기 전용" 원칙은 의뢰 #3에 적용되지 않습니다. crawling은 이 건에서 데이터 공급(기존 bsight `sales_record` 적재)만 담당하며 신규 API·전송은 없습니다.

## 3. 의뢰 상세

### 의뢰 #1 — 쿠팡 로켓그로스 재고 현황 조회 화면

**상태: 확정** — 아래 스키마/API는 최종본이며, crawling 배포 완료 시점에 "전달됨"으로 변경 후 작업 시작하면 됨.

#### 1-1. 배경

crawling이 쿠팡 오픈 API로 로켓그로스(로켓창고) 재고를 주기적으로 수집해 `coupang_inventory` 테이블에 최신 스냅샷을 유지한다(vendorItemId 기준 upsert). 이 재고 현황을 조회하는 화면과, 필요 시 실시간 값을 가져오는 새로고침 기능을 만든다.

#### 1-2. 테이블 명세 (참고용 — 생성은 crawling이 함)

```sql
-- ⚠️ 실행하지 마세요. 이 SQL은 컬럼 구조 파악을 위한 참고용 명세입니다.
-- 테이블은 crawling(Spring JPA)이 자동 생성하며, 30-we.com은 조회만 합니다.
CREATE TABLE coupang_inventory (
    inventory_id             BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
    vendor_item_id           BIGINT       NOT NULL,                -- 쿠팡 옵션(SKU) 고유 ID
    external_sku_id          VARCHAR(100) NULL,                    -- 판매자 정의 SKU ID
    product_name             VARCHAR(500) NULL,                    -- 상품명 (상품 API에서 매핑, 매핑 전 NULL 가능)
    orderable_quantity       INT          NOT NULL,                -- 로켓창고 주문 가능 수량
    sales_count_last_30_days INT          NULL,                    -- 최근 30일 판매 수량
    collected_at             DATETIME(6)  NOT NULL,                -- 마지막 동기화 시각
    UNIQUE KEY uk_vendor_item_id (vendor_item_id)
);
```

- 항상 "옵션(SKU)당 1행"인 최신 스냅샷이다. 이력 테이블이 아니다.
- `product_name`은 NULL일 수 있으므로 화면에서 `{{$item->product_name ?? '(상품명 미매핑)'}}` 처리.

#### 1-3. Eloquent 모델 (전체 코드)

`app/Models/CoupangInventory.php` 신규 생성:

```php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Model;

class CoupangInventory extends Model
{
    protected $connection = 'mysql_bsight';
    protected $table = 'coupang_inventory';
    protected $primaryKey = 'inventory_id';
    public $timestamps = false; // created_at/updated_at 없음. collected_at만 존재

    protected $casts = [
        'collected_at' => 'datetime',
    ];
}
```

#### 1-4. 라우트 (routes/web.php)

기존 bsight 그룹(`routes/web.php:989` 부근, `['prefix' => 'bsight', 'as' => 'bsight::', 'middleware'=>['admin.access']]`)과 **같은 레벨에** 아래 그룹을 추가:

```php
Route::group(
    ['prefix' => 'coupang', 'as' => 'coupang::', 'middleware' => ['admin.access']],
    function () {
        Route::get('inventory-list', [\App\Http\Controllers\Admin\CoupangController::class, 'inventoryList'])->name('inventoryList');
        Route::get('inventory-realtime', [\App\Http\Controllers\Admin\CoupangController::class, 'inventoryRealtime'])->name('inventoryRealtime');
        Route::get('restock-list', [\App\Http\Controllers\Admin\CoupangController::class, 'restockList'])->name('restockList'); // 의뢰 #2
    }
);
```

라우트 헬퍼는 기존 관례대로 `route("admin::coupang::inventoryList")` 형태가 된다.

#### 1-5. 컨트롤러 (전체 코드)

`app/Http/Controllers/Admin/CoupangController.php` 신규 생성. BsightController::productList 패턴(권한 체크, 필터, paginate)을 그대로 따름:

```php
<?php

namespace App\Http\Controllers\Admin;

use App\Http\Controllers\Controller;
use App\Models\CoupangInventory;
use App\Models\CoupangRestockSuggestion;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Auth;
use Illuminate\Support\Facades\Http;
use Illuminate\Support\Facades\Log;

class CoupangController extends Controller
{
    // [의뢰 #1] 재고 현황 목록 (패턴 A: DB 조회)
    public function inventoryList(Request $request)
    {
        $items = CoupangInventory::whereRaw('1=1');

        if ($request->get('query')) {
            $query = $request->get('query');
            $items = $items->where(function ($q) use ($query) {
                $q->where('product_name', 'like', "%{$query}%")
                  ->orWhere('external_sku_id', 'like', "%{$query}%");
            });
        }

        $item_count = $items->count();
        $last_collected_at = CoupangInventory::max('collected_at'); // 마지막 동기화 시각

        $orderByWhich = $request->get('orderByWhich');
        if ($orderByWhich) {
            $orderByExploded = explode(' ', $orderByWhich);
            $items = $items->orderBy($orderByExploded[0], $orderByExploded[1])->paginate(40);
        } else {
            $items = $items->orderBy('orderable_quantity', 'asc')->paginate(40); // 기본: 재고 적은 순
        }

        if (Auth::user()->hasRole(['system_admin', 'idus_admin'])) {
            $data = [
                'items' => $items,
                'item_count' => $item_count,
                'last_collected_at' => $last_collected_at,
                'realtime' => false,
            ];
            return view('admin.coupang.inventory_list', $data);
        } else {
            echo "<script>alert('권한 없는 페이지입니다.');history.back();</script>";
        }
    }

    // [의뢰 #1] 실시간 재고 조회 (패턴 B: crawling 내부 API 호출)
    public function inventoryRealtime(Request $request)
    {
        if (!Auth::user()->hasRole(['system_admin', 'idus_admin'])) {
            echo "<script>alert('권한 없는 페이지입니다.');history.back();</script>";
            return;
        }

        try {
            $response = Http::withHeaders([
                'X-Internal-Token' => config('services.crawling.internal_token'),
            ])->timeout(15)->get(config('services.crawling.base_url') . '/internal/coupang/inventory');

            if (!$response->successful()) {
                Log::error('crawling 실시간 재고 API 오류', [
                    'status' => $response->status(),
                    'body' => $response->body(),
                ]);
                return redirect()->route('admin::coupang::inventoryList')
                    ->with('error', '실시간 조회에 실패했습니다. 마지막 동기화 데이터를 표시합니다.');
            }

            $result = $response->json();
            // 실시간 결과는 페이징 없이 전체 표시 (SKU 수십~수백 개 수준)
            $data = [
                'items' => collect($result['items']),
                'item_count' => count($result['items']),
                'last_collected_at' => $result['collectedAt'],
                'realtime' => true,
            ];
            return view('admin.coupang.inventory_list', $data);
        } catch (\Exception $e) {
            Log::error('crawling 실시간 재고 API 연결 실패', ['message' => $e->getMessage()]);
            return redirect()->route('admin::coupang::inventoryList')
                ->with('error', '실시간 조회에 실패했습니다. 마지막 동기화 데이터를 표시합니다.');
        }
    }

    // [의뢰 #2] 부족 재고 / 입고 제안 목록 — 의뢰 #2 참고
    public function restockList(Request $request)
    {
        // 의뢰 #2의 코드 참고
    }
}
```

주의: `$items`가 실시간 모드에서는 Collection, DB 모드에서는 Paginator이므로 blade에서 `$realtime` 플래그로 분기한다 (아래 뷰 명세 참고). PHP 7.3 환경이므로 arrow function(`fn()`)·nullsafe(`?->`) 사용 금지 — 위 코드는 모두 7.3 호환.

#### 1-6. crawling 내부 API 명세 (패턴 B, crawling이 제공)

```
GET {CRAWLING_BASE_URL}/internal/coupang/inventory
Header: X-Internal-Token: {토큰}
```

성공 응답 `200`:

```json
{
  "collectedAt": "2026-08-21T14:30:00",
  "items": [
    {
      "vendorItemId": 70000000000,
      "externalSkuId": "10012345",
      "productName": "상품명 (미매핑이면 null)",
      "orderableQuantity": 10,
      "salesCountLast30Days": 15
    }
  ]
}
```

오류 응답:

| status | body | 30-we.com 처리 |
|---|---|---|
| 401 | `{"error": "unauthorized"}` | 토큰 설정 확인 필요. 목록으로 리다이렉트 + 오류 메시지 |
| 502 | `{"error": "coupang_api_error", "message": "..."}` | 쿠팡 쪽 오류. 목록으로 리다이렉트 + 오류 메시지 |
| (연결 실패/타임아웃) | - | 목록으로 리다이렉트 + 오류 메시지 (컨트롤러 catch 블록) |

- crawling 내부에 1분 TTL 캐시가 있으므로 연타해도 안전하다. 30-we.com에서 별도 스로틀링 불필요.
- 실시간 조회 결과는 crawling이 `coupang_inventory` 스냅샷에도 반영하므로, 새로고침 직후에는 목록 화면(패턴 A)의 데이터와 마지막 동기화 시각도 함께 최신화된다.

#### 1-7. 뷰

`resources/views/admin/coupang/inventory_list.blade.php` 신규 생성. **`resources/views/admin/bsight/product_list.blade.php`를 복사해서 수정하는 것을 권장** (같은 레이아웃 `layouts.uknowad`, 같은 breadcrumb/card/페이징 구조).

화면 구성:

1. breadcrumb: `쿠팡 로켓그로스 > 재고 현황 :: {{number_format($item_count)}} 개`
2. 상단 우측: 마지막 동기화 시각 + 새로고침 버튼
   ```php
   @if ($realtime)
       <span class="badge badge-success">실시간 조회 결과</span>
   @else
       <span>마지막 동기화: {{$last_collected_at}}</span>
   @endif
   <a type="button" class="btn btn-warning" href="{{route('admin::coupang::inventoryRealtime')}}">지금 새로고침</a>
   ```
3. 오류 플래시 표시:
   ```php
   @if (session('error'))
       <div class="alert alert-danger">{{session('error')}}</div>
   @endif
   ```
4. 검색 폼 (GET, 패턴 A에서만): 검색어 `query`(상품명/SKU ID), 정렬 `orderByWhich` — 옵션: `orderable_quantity asc`(재고 적은 순, 기본), `orderable_quantity desc`, `sales_count_last_30_days desc`(판매 많은 순)
5. 테이블 컬럼:

   | 헤더 | 값 (DB 모드) | 값 (실시간 모드) |
   |---|---|---|
   | 상품명 | `{{$item->product_name ?? '(미매핑)'}}` | `{{$item['productName'] ?? '(미매핑)'}}` |
   | SKU ID | `{{$item->external_sku_id}}` | `{{$item['externalSkuId']}}` |
   | 옵션 ID | `{{$item->vendor_item_id}}` | `{{$item['vendorItemId']}}` |
   | 주문가능수량 | `{{number_format($item->orderable_quantity)}} 개` | `{{number_format($item['orderableQuantity'])}} 개` |
   | 최근 30일 판매 | `{{number_format($item->sales_count_last_30_days)}} 개` | `{{number_format($item['salesCountLast30Days'])}} 개` |

   구현 단순화를 위해 blade 상단에서 실시간 모드일 때 배열을 객체 형태로 변환해도 됨:
   ```php
   @php
       if ($realtime) {
           $items = $items->map(function ($row) {
   ```

### 의뢰 #3 — 영풍문고 발송 업무 자동화

**상태: 초안** — 착수 전 아래 "3-0. 선행 실측"을 먼저 수행해 상품 매칭율을 확인한 뒤 진행. 매칭율이 낮으면 담당자와 협의.

> **이 의뢰는 예외입니다.** 30-we가 이미 보유한 Trade 모듈(거래명세서·로젠 송장·팝빌 문자·재고 로그)을 사용하므로 **읽기 전용이 아니라 쓰기·액션까지 30-we가 수행**합니다. crawling은 기존대로 영풍 판매를 `bsight.sales_record`에 적재만 하며(이미 운영 중), 이 건에 신규 API·전송은 없습니다.

#### 3-0. 배경 및 업무 흐름

영풍문고 발송 담당자의 수작업(① 영풍 SCM에서 판매내역 확인 → ② 지점별 엑셀에 판매수량 수기 입력·잔여재고 계산 → ③ 거래명세서·발송내역서·송장 작성 → ④ 발송 → ⑤ 지점 안내 문자)을 자동화한다. ①②는 이미 crawling이 매일 `sales_record`에 수집하므로, 30-we는 **그 데이터를 읽어 "부족재고 감지 → 관리자 발송수량 입력 → 문서 자동생성"** 을 담당한다.

**전체 흐름 (매일 + 발송 시점):** *(2026-08-26 확정 도식 반영)*
```
[매일 08:00] trade:detectLowStock (신규 커맨드)
   위탁거래처(영풍 지점) × 상품별  현재고 = 재고로그 합산 − bsight 판매량
   → 현재고 <= 설정임계치(stock_alert_qty) 이면 부족재고
   → Slack 알림 (지점·상품·현재고·임계치) + 바코드 미매칭 경고

[관리자] "부족재고 발송" 전용 화면(영풍 탭)에서 부족 목록 확인
   → 상품 추가/삭제 (부족 목록 외 추가 발송분 반영)
   → 지점×상품 발송수량 입력 → 생성 버튼
   → createShipment (신규): 거래명세서(위탁) 생성 → 발송내역서 PDF
   → 미리 등록한 지점 정보(주소·연락처) 기반 로젠 송장 발급·출력
   → (물리작업: 패킹·내역서 동봉·송장부착)
   → 관리자 [발송] 버튼 → 재고 자동 차감 + 해당 지점에 템플릿 문자 자동 전송(송장번호 포함)
```

**핵심 전제 — 상품 매칭:** bsight `product.product_code`(영풍 바코드) 와 30-we `TradeProduct` 바코드(`barcode_list`)를 **완전일치(=)** 로 매칭한다. 매칭 안 된 상품은 판매 집계에서 빠져 재고가 실제보다 많게 보이므로(→ 부족감지 누락, 발주 사고), 반드시 경고를 노출한다.

**crawling 측 데이터 실측 결과(2026-08, 참고):** 영풍 판매 상품 102종 전부 13자리 순수숫자(EAN-13), 공백·특수문자 없음. bsight product 전체 214종 중 213종이 정상 13자리(1종은 빈 코드 유령 레코드). 즉 바코드 품질은 양호하며, 매칭 실패가 있다면 대부분 "30-we `TradeProduct`에 해당 바코드가 미등록"인 경우다.

#### 3-0-2. 바코드 정규화 정합성 (양쪽 동일 규칙 — 30-we도 적용)

매칭은 `bsight.product_code == TradeProduct 바코드` **완전일치**이므로, 한쪽에만 공백/특수문자가 섞이면 조용히 매칭 실패한다(silent failure). **양쪽이 동일한 정규화 규칙**을 적용해야 안전하다.

- **규칙(양쪽 공통):** 앞뒤·내부의 모든 공백류(스페이스/탭/개행/NBSP) 제거, 결과가 빈 문자열이면 저장하지 않음. **"숫자만 남기기" 같은 공격적 변형은 금지**(ISBN 부가기호·비도서 코드 손상 위험).
- **crawling 측(이미 완료):** 저장 시 정규화 적용 완료(`BarcodeNormalizer`). 기존 bsight 214종 전수 검증 결과 **정규화해도 값이 바뀌는 것 0건**(이미 깨끗). 즉 정규화로 기존 데이터가 다른 값이 되어 중복 생성될 위험 없음.
- **30-we 측(이 의뢰에 포함):**
  1. **신규 등록 정규화** — `TradeProduct` 바코드(및 `TradeProductBarcode`) **등록/수정 저장 시** 위 규칙으로 정규화. `postProduct`/바코드 저장 지점에 `preg_replace('/[\s\x{00A0}]/u', '', trim($barcode))` 적용(PHP 7.3 호환) 후, 빈값이면 저장 스킵.
  2. **기존 데이터 소급 정리(1회)** — `trade_products.barcode` + `trade_product_barcodes.barcode`의 기존 값 중 정규화하면 달라지는 것이 있는지 먼저 조회하고(읽기 전용), 있으면 1회 UPDATE로 정리. **수기 입력이라 crawling보다 공백 위험이 높으므로 반드시 확인.** 소급 UPDATE 전 백업 권장.

> 주의: 신규만 정규화하고 기존을 두면, 기존에 공백 든 바코드는 계속 매칭 실패한다. 그래서 소급 정리가 필요하다.

#### 3-0-1. 선행 실측 (착수 전, 읽기 전용 — 30-we 환경에서 수행)

30-we의 `mysql_bsight` 커넥션과 메인 DB를 모두 볼 수 있는 30-we 환경에서, 영풍 판매 상품이 `TradeProduct` 바코드와 얼마나 매칭되는지 측정한다(예: tinker). 매칭율이 낮으면 `TradeProduct` 바코드 등록을 선행해야 한다.

```php
// tinker 예시 — 영풍 판매 상품코드 중 TradeProduct 바코드와 매칭되는 비율
$codes = DB::connection('mysql_bsight')->table('sales_record as sr')
    ->join('product as p', 'sr.product_id', '=', 'p.product_id')
    ->join('sales_location as l', 'sr.location_id', '=', 'l.location_id')
    ->where('l.location_name', 'Yeongpoong')
    ->distinct()->pluck('p.product_code');           // 영풍 판매 상품코드
$total = $codes->count();
// TradeProduct 다중바코드(barcode_list) 전체 집합 구성 후 교집합 카운트
// (barcode_list는 TradeProductBarcode.barcode + 레거시 trade_products.barcode)
```

#### 3-1. 임계치(발주 기준 수량) 설정 — 기존 기능 재사용, 신규 없음

부족 판정 기준값은 **거래처×상품별 `TradePartnerProduct.stock_alert_qty`** 다. 이미 설정 UI/엔드포인트가 존재하므로 신규 구현 불필요:
- `TradeController::updatePartnerProductAlert` (`app/Http/Controllers/Admin/TradeController.php:2236` 부근) — 다중 선택 임계치 업데이트
- `TradeController::savePartnerProductAlert` (2129 부근) — 거래처-제품 연결 시 임계치 입력
- (보관장소용) `TradeController::saveLocationAlert` (8537 부근), `bulkUpdateLocationAlerts` (8559 부근)

임계치는 언제든 수정 가능. 영풍 각 지점(=위탁 거래처)의 상품별 기준 수량을 이 화면에서 세팅해두면 된다.

**추가 설정 — "발송 권장 합계"(지점 단위):** 실무에서 재고가 1~2개로 급한 경우가 아니면, **한 지점의 부족 상품 수량 합계가 일정 수(예: 20개) 이상 모였을 때 모아서 발송**한다. 이 값은 **고정하지 말고 설정값**으로 둔다(임계치처럼 조정 가능하게).

```php
$salesRecords = DB::connection('mysql_bsight')
    ->table('sales_record')
    ->join('product', 'sales_record.product_id', '=', 'product.product_id')
    ->where(function ($query) use ($locationFromDates, $today) {
        foreach ($locationFromDates as $locationId => $fromDate) {
            $query->orWhere(function ($q) use ($locationId, $fromDate, $today) {
                $q->where('sales_record.location_id', $locationId)
                  ->whereBetween('sales_record.sales_date', [$fromDate, $today]);
            });
        }
    })
    ->whereIn('product.product_code', array_values($productBarcodes))  // TradeProduct 바코드들
    ->select('sales_record.location_id', 'product.product_code',
             DB::raw('SUM(sales_record.quantity) as total_qty'))
    ->groupBy('sales_record.location_id', 'product.product_code')
    ->get();
```

**커맨드 골격 (전체 코드):**

```php
<?php

namespace App\Console\Commands;

use App\Models\TradePartner;
use App\Models\TradePartnerProduct;
use App\Models\TradeProduct;
use App\Services\TradeInventoryService;
use Illuminate\Console\Command;

class DetectLowStockTrade extends Command
{
    protected $signature = 'trade:detectLowStock {--user=} {--dry-run}';
    protected $description = '위탁 거래처(영풍 등) 부족재고 감지 및 Slack 알림';

    // ALLOWED_USER_IDS = [1, 19603] (TradeController와 동일)
    private $targetUserIds = [1, 19603];

    public function handle(TradeInventoryService $inventory)
    {
        $userOpt = $this->option('user');
        $userIds = $userOpt ? [(int) $userOpt] : $this->targetUserIds;
        $dryRun = (bool) $this->option('dry-run');

        foreach ($userIds as $userId) {
            $result = $inventory->detectShortages($userId);   // [{partner, product, current, alertQty}], + unmatched
            $shortages = $result['shortages'];
            $unmatched = $result['unmatched'];

            if (empty($shortages) && empty($unmatched)) {
                $this->info("user {$userId}: 부족재고 없음");
                continue;
            }

            $msg = $this->buildMessage($userId, $shortages, $unmatched);
            $this->info($msg);
            if (!$dryRun) {
                $this->sendSlack($msg);
            }
        }
        return 0;
    }

    private function buildMessage($userId, array $shortages, array $unmatched)
    {
        $lines = ["# 부족재고 알림 (user {$userId})"];
        foreach ($shortages as $s) {
            $lines[] = "· {$s['partner_name']} / {$s['product_name']}: 현재 {$s['current']}개 (임계 {$s['alert_qty']})";
        }
        if (!empty($unmatched)) {
            $lines[] = "\n⚠️ 바코드 미매칭 " . count($unmatched) . "건 (집계 누락 가능): "
                     . implode(', ', array_slice($unmatched, 0, 20));
        }
        return implode("\n", $lines);
    }

    // BsightLibrarySalesReport::send_slack(37-79) 패턴. 단 웹훅은 config로.
    private function sendSlack($message)
    {
        $url = config('trade.slack_webhook');   // config/trade.php: env('TRADE_SLACK_WEBHOOK')
        if (!$url) return;
        $payload = ['blocks' => [['type' => 'section', 'text' => ['type' => 'mrkdwn', 'text' => $message]]]];
        $ch = curl_init();
        curl_setopt_array($ch, [
            CURLOPT_URL => $url, CURLOPT_RETURNTRANSFER => true, CURLOPT_TIMEOUT => 30,
            CURLOPT_CUSTOMREQUEST => 'POST', CURLOPT_POSTFIELDS => json_encode($payload),
            CURLOPT_HTTPHEADER => ['Content-Type: application/json'],
        ]);
        curl_exec($ch);
        curl_close($ch);
    }
}
```

`TradeInventoryService::detectShortages($userId)` 가 할 일 (getInventory 로직 재사용):
1. 위탁 거래처: `TradePartner::forUser($userId)->active()->where('trade_type', TradePartner::TRADE_TYPE_CONSIGNMENT)->get()` (bsight_location_id 있는 것만).
2. 활성 제품: `TradeProduct::forUser($userId)->active()->with('barcodes')->get()` → `barcode_list`로 `barcodeToProductId` 맵.
3. `calculateStockByPlace` + `appendInTransitStock` + bsight 판매차감(위 SQL) → 거래처별 현재고.

6. bsight에서 팔렸는데 `barcodeToProductId`에 없는 product_code = `unmatched`(미매칭 경고).

```php
    $items = $request->get('items', []);        // [{product_id, product_name, barcode, quantity, unit_price, sale_price}]

    // 발송수량 > 0 인 아이템만
    $validItems = [];
    foreach ($items as $it) {
        if (!empty($it['quantity']) && (int) $it['quantity'] > 0) {
            $validItems[] = $it;
        }
    }
    if (empty($partnerId) || empty($validItems)) {
        return response()->json(['isSuccess' => false, 'message' => '발송할 항목이 없습니다.'], Response::HTTP_OK);
    }

    $isSuccess = true;
    $message = '';
    $supplyId = null;
    $logen = null;

    try {
        // 1) 위탁 거래명세서 생성 (SupplyService 재사용)
        $supply = app(\App\Services\SupplyService::class)->createSupply($user, [
            'partner_id'            => $partnerId,
            'supply_type'           => TradeSupply::SUPPLY_TYPE_CONSIGNMENT,
            'supply_date'           => $request->get('supply_date', now()->toDateString()),
            'delivery_date'         => $request->get('delivery_date'),
            'ship_from_location_id' => $request->get('ship_from_location_id'),
            'items'                 => $validItems,
        ]);
        $supplyId = $supply->id;

        // 2) 로젠 송장 발급 (logenPrintForSupplies 재사용) — 재고 차감은 여기서 하지 않음(출력확인 시점)
        $logen = $this->logenPrintForSupplies($user->id, [$supply->id]);
        // $logen = ['slips'=>[...], 'skipped'=>[...], 'failed'=>[...]]

    } catch (\Exception $e) {
        $isSuccess = false;
        $message = $e->getMessage();
    }

    return response()->json([
        'isSuccess'   => $isSuccess,
        'message'     => $message,
        'supply_id'   => $supplyId,                                   // 발송내역서 PDF 다운로드에 사용
        'pdf_url'     => $supplyId ? route('admin::...trade::downloadSupplyPdf', ['id' => $supplyId]) : null,
        'slips'       => $logen ? $logen['slips'] : [],               // 로젠 송장 출력 데이터
        'logen_failed'=> $logen ? $logen['failed'] : [],             // 부분 실패 목록(있으면 UI에 표시)
    ], Response::HTTP_OK);
}
```
> 라우트 헬퍼 `admin::...trade::downloadSupplyPdf`는 기존 PDF 라우트 이름으로 교체(현행 등록명 확인).

**(4) 발송내역서 PDF** — `downloadSupplyPdf($request, $supplyId)`(3779-3837) 그대로 재사용. 위탁이면 `shipment_pdf.blade.php`(금액 미표시) 자동 선택(3792-3808). UI는 응답의 `pdf_url`을 새 탭/다운로드로 연다. 다건은 `downloadBulkSupplyPdf`(3843).

**(5) 로젠 송장 출력** — 응답 `slips`를 기존 로젠 출력 UI(현행 logenPrint 결과를 출력하던 화면/JS)와 동일하게 처리. `logen_failed`가 있으면 "N건 실패: ..." 요약 표시.

**(6)+(7) [발송] 버튼 — 재고 차감 + 문자 자동 전송** *(2026-08-26 확정 도식 반영: 기존 "로젠 출력 확인"과 "문자 발송하기" 두 동작을 [발송] 버튼 하나로 통합)*

createShipment는 차감하지 않는다. 패킹·송장부착이 끝난 뒤 관리자가 **[발송] 버튼**을 누르면 아래 두 가지가 순서대로 실행된다:

1. **재고 차감(기존 흐름 재사용):** `logenPrintConfirm`(4276-4364) → `confirmDelivery`(delivered_at) → `applyDeliveryInventoryLogs`(3133-3220): 위탁발송이면 `TradeInventoryLog::TYPE_SUPPLY_OUT`(from=출고장소, to=거래처). 이중차감·되돌리기 방지를 위해 이 시점에만 차감.
2. **발송 안내 문자 자동 전송:** 이어서 같은 요청 안에서 기존 `sendDeliverySms`(3320-3362) 로직을 호출(입력: `supply_id`)해 해당 지점(거래처)으로 템플릿 문자를 전송한다. 문자 실패 시 차감은 유지하고 "문자 전송 실패 — 재전송" 버튼을 행에 노출한다(차감·문자를 트랜잭션으로 묶지 않는다).

- 버튼 명칭은 [발송] (교보 쪽 [배송대기]와 역할 동일 — 명칭 통일은 UI에서 조정 가능).
- `sendDeliverySms`는 **이미 구현돼 있어 그대로 사용**하며, [발송] 처리에서 내부 호출로 연결만 하면 된다.
- 문구는 `buildDeliverySmsMessage`(3368-3389)가 `TradeSetting`에 저장된 템플릿을 불러와 `{거래처명}{송장번호}{명세서번호}` 등을 `strtr`로 치환한다(자유 편집 가능, 기존 템플릿 관리 UI `getDeliverySmsTemplates`/`saveDeliverySmsTemplates` 3425 재사용).
- 실제 전송: `PopbillApi::sendBsightSms($receiver, $content, $subject, $name)`(1098). 수신번호는 `TradePartner.contact_number`.
- 라우트: 기존 `send-delivery-sms`가 이미 있으면 그대로 버튼에 연결. 없으면 trade 그룹에 `POST send-delivery-sms` 추가(현행 확인).
- **주의:** 송장번호가 채워진 뒤(로젠 발급 후)에 눌러야 `{송장번호}`가 정상 치환된다.

**응답/에러 요약(UI 처리):**
- 성공: `isSuccess=true`, `pdf_url`로 발송내역서 열기 + `slips`로 송장 출력.
- 명세서 실패: `isSuccess=false` + `message` 표시(생성 안 됨).
- 명세서는 됐으나 로젠 부분실패: `isSuccess=true`지만 `logen_failed` 비어있지 않음 → "송장 일부 실패" 경고와 함께 성공분만 진행.

#### 3-5. 지점(거래처) 정보 등록 — 기존 기능 재사용, 신규 UI 없음

송장·문자에 필요한 **지점별 주소·연락처는 기존 "거래처 등록" 기능에 이미 있다.** 별도 화면을 새로 만들지 말 것.

- 영풍 각 지점을 **위탁 거래처(`TradePartner`, `trade_type=consignment`)로 1개씩 등록**한다. 기존 `TradeController::postPartner`(226-275)가 아래를 모두 받는다:
  - `name`(지점명), `contact_number`(문자 수신번호), `address`(송장 주소), `bsight_location_id`(영풍 `sales_location.id`와 연결 — 판매 집계 매칭 키), `business_number`/`owner`/`email` 등.
- 명세서 생성 시 이 거래처 정보가 수취인으로 자동 반영된다(`TradeSupply.resolved_receiver_*` — 명세서에서 별도 입력하면 그 값 우선, 없으면 거래처 기본값). 즉 **송장의 주소·수취인은 거래처에 등록해두면 자동**이다.
- 따라서 "지점별 주소 입력하는 곳"은 **기존 거래처 등록/수정 화면** 그대로다. 운영에서 영풍 36개 지점을 위탁 거래처로 등록하고 `bsight_location_id`를 매핑하면 된다.

> ⚠️ `bsight_location_id` 매핑이 빠지면 그 지점 판매가 재고에서 차감되지 않는다(부족감지 누락). 지점 등록 시 필수.

#### 3-5-1. 초기 재고 입력 (운영 준비 — 코드 아님)

### 의뢰 #4 — 쿠팡 매출(판매) 조회 화면

### 의뢰 #5 — 쿠팡 판매자배송 주문 화면 + 출고 처리

**상태: 확정** — crawling 구현 완료. 배포 후 "전달됨"으로 변경.
**예외 유형** (의뢰 #3과 동일): 30-we가 읽기 전용이 아니라 **액션(로젠 송장 발급, crawling API 호출)까지 수행**한다.

#### 5-1. 배경과 전체 그림

판매자배송(마켓플레이스) 주문은 판매자가 직접 출고해야 한다. crawling이 주문을 수집해 bsight DB에 적재하고 하루 2회(09/12시) 슬랙 다이제스트를 보낸다. **30-we.com은 주문 화면과 출고 버튼 2개를 맡는다:**

```
[crawling]  주문 수집 → bsight DB 적재 → 슬랙 다이제스트(09/12시)
[30-we]     주문 화면(수취인 상세 포함)
             → [버튼A 송장 발급]  로젠 발급 + 라벨 인쇄 (재발급 자유)
             → 사람 검수
             → [버튼B 쿠팡 등록]  crawling 내부 API 호출 → 쿠팡 준비중+송장 등록
[crawling]  쿠팡 API 호출 수행 + 주문 행에 처리 상태 기록
```

버튼을 분리한 이유: 로젠 송장은 내부 작업(재발급 자유), 쿠팡 등록은 고객 노출(수습 어려움) — 사이에 사람 검수를 둔다.
**30-we는 crawling 테이블(coupang_marketplace_order*)에 쓰지 않는다** — 읽기만. 출고 상태는 버튼B가 호출하는 내부 API가 crawling 쪽에서 기록한다.

#### 5-2. 읽을 테이블 명세 (bsight DB, `mysql_bsight` 커넥션)

```sql
-- ⚠️ 실행하지 마세요. 참고용 명세입니다 (crawling JPA가 생성·관리, 30-we는 조회만).
CREATE TABLE coupang_marketplace_order (
    marketplace_order_id  BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
    order_id              BIGINT       NOT NULL,        -- 쿠팡 주문번호
    shipment_box_id       BIGINT       NULL,
```

```php
public function issueWaybill(Request $request, $orderId)
{
    $order = CoupangMarketplaceOrder::where('order_id', $orderId)->first();
    if (!$order) {
        return response()->json(['error' => '주문을 찾을 수 없습니다'], 404);
    }
    if ($order->shipped_at) {
        return response()->json(['error' => '이미 쿠팡에 등록 완료된 주문입니다'], 409);
    }

    $items = $order->items;
    $firstName = $items->first() ? $items->first()->product_name : '상품';
    $itemLabel = $items->count() > 1 ? $firstName . ' 외 ' . ($items->count() - 1) . '건' : $firstName;

    $service = app(\App\Services\WaybillIssuanceService::class);
    try {
        $result = $service->issue(
            $order->receiver_name,
            $order->receiver_phone,
            trim($order->receiver_addr1 . ' ' . $order->receiver_addr2),
            $itemLabel,
            'CP' . $order->order_id
        );
    } catch (\Exception $e) {
        return response()->json(['error' => '로젠 발급 실패: ' . $e->getMessage()], 502);
    }

    TradeCoupangWaybill::updateOrCreate(
        ['order_id' => $order->order_id],
        [
            'user_id' => Auth::id(),
            'delivery_company_code' => 'LOGEN',
            'tracking_number' => $result['tracking_number'],
            'issued_at' => now(),
            'registered_at' => null, // 재발급 시 등록 상태 초기화
        ]
    );

    return response()->json([
        'tracking_number' => $result['tracking_number'],
        'slip' => $result['slip'], // 라벨 출력 팝업용 (기존 logen_print_js 재사용)
    ]);
}

// [의뢰 #5 - 버튼B] 쿠팡 등록 (crawling 내부 API 호출 — 준비중 처리 + 송장 등록)
public function registerCoupang(Request $request, $orderId)
{
    $waybill = TradeCoupangWaybill::where('order_id', $orderId)->first();
    if (!$waybill) {
        return response()->json(['error' => '송장을 먼저 발급해주세요'], 400);
    }
    if ($waybill->registered_at) {
        return response()->json(['error' => '이미 등록된 송장입니다: ' . $waybill->tracking_number], 409);
    }

    $response = Http::withHeaders([
        'X-Internal-Token' => config('services.crawling.internal_token'),
    ])->timeout(30)->post(
        config('services.crawling.base_url') . '/internal/coupang/orders/' . $orderId . '/ship',
        [
            'deliveryCompanyCode' => $waybill->delivery_company_code,
            'invoiceNumber' => $waybill->tracking_number,
        ]
    );

    if (!$response->successful()) {
        $body = $response->json();
        $message = isset($body['message']) ? $body['message'] : $response->body();
        Log::error('쿠팡 출고 등록 실패', ['orderId' => $orderId, 'status' => $response->status(), 'body' => $body]);
        return response()->json(['error' => '쿠팡 등록 실패: ' . $message], $response->status());
    }

    $waybill->update(['registered_at' => now()]);
    return response()->json($response->json()); // {orderId, acknowledged, invoiceRegistered, trackingNumber, ...}
}
```

#### 5-8. crawling 내부 API 계약 (구현 완료 — 버튼B가 호출)

```
POST {CRAWLING_BASE_URL}/internal/coupang/orders/{쿠팡주문번호}/ship
Header: X-Internal-Token: {토큰}
Body:   {"deliveryCompanyCode": "LOGEN", "invoiceNumber": "12345678901"}
```

동작: 쿠팡에 **① 상품준비중 처리(이미 처리됐으면 건너뜀) → ② 송장 등록**을 순차 수행하고 bsight 주문 행에 상태를 기록한다. ①만 성공하고 ②가 실패한 경우 **같은 요청을 재호출하면 ②부터 재시도**된다(멱등).

성공 `200`:
```json
{"orderId": 28000012345678, "acknowledged": true, "invoiceRegistered": true,
 "deliveryCompanyCode": "LOGEN", "trackingNumber": "12345678901",
 "message": "출고 처리 완료 (준비중 처리 + 송장 등록)"}
```

| status | body.error | 의미 / 30-we 처리 |
|---|---|---|
| 401 | unauthorized | 토큰 확인 |
| 404 | order_not_found | crawling에 없는 주문번호 |
| 409 | invalid_state | 이미 등록된 주문 등 — 메시지 그대로 표시 |
| 400 | bad_request | 파라미터 누락 |
| 502 | coupang_api_error | 쿠팡 쪽 오류 — 메시지 표시 후 재시도 안내 |

- 택배사 코드는 `"LOGEN"`(로젠). 쿠팡이 코드 오류를 반환하면 쿠팡 개발자센터 "택배사 코드" 문서로 재확인.
- 송장번호 규칙: 쿠팡은 6개월 내 중복 송장번호를 거부한다 (로젠 신규 발급 번호면 문제 없음).

### 의뢰 #6 — 교보문고(핫트랙스) 발주 자동화

**상태: 확정** — crawling 구현 완료. 배포 후 "전달됨"으로 변경.
**예외 유형** (의뢰 #3·#5와 동일): 30-we가 읽기 전용이 아니라 **액션(거래명세서 생성, crawling API 호출)까지 수행**한다.

#### 6-1. 배경과 전체 그림

의뢰 #3(영풍)은 **우리가 파는 것**(판매→발송)이었지만, 교보는 **방향이 반대**다. 교보(핫트랙스 Partner Portal)가 우리(비사이트, 협력사코드 `0817671`)에게 **발주**를 넣으면 우리가 납품한다. crawling이 발주를 수집해 bsight DB에 적재하고 **매일 12:00 1회** 슬랙 다이제스트(전날 12:00 이후 수집분)를 보낸다. **30-we.com은 가거래명세서 자동 생성 + 발주 화면 + [확정]/[배송대기(납품확인)] 버튼을 맡는다:** *(2026-08-26 확정 도식 반영)*

```
[crawling]  1시간마다 핫트랙스 접속 → 발주 목록·상세 수집 + [엑셀출력] 원본 엑셀 저장 → bsight DB 적재
             → 슬랙 다이제스트(매일 12:00 1회 — 전날 12:00 이후 수집분)
[30-we]     (자동) 신규 발주 감지 → 바코드 매칭 → 가거래명세서(위탁, 미확정) 자동 생성  ← 스케줄 커맨드
[30-we]     발주 목록 화면 (작업자 12:00 접속)
             → 가거래명세서·실물 재고 확인 (수량 수정은 supply_detail에서)
             → [확정] 버튼         가거래명세서 → 정식 거래명세서 확정
             → 교보 원본 엑셀 출력 → (물리 작업: 엑셀 동봉 포장)
             → [배송대기(납품확인)] 버튼:
                ① crawling 내부 API 호출 → 핫트랙스 납품확인 봇 실행
                ② 로젠 송장 발급 (수하인 = 지점 거래처 주소) + 송장번호 저장·라벨 출력
                ③ 지정 템플릿 문자 자동 전송 (지점 담당자, 송장번호 포함)
[crawling]  핫트랙스 봇(Selenium) 실행 + 발주 행에 처리 상태 기록
```

[확정](내부 작업, 수정 자유)과 [배송대기(납품확인)](외부 노출, 수습 어려움)를 분리하고 사이에 사람 검수(실물 재고 확인·포장)를 두는 원칙은 의뢰 #5와 같다. 가거래명세서는 **자동 생성 시점에는 아무 외부 효과가 없으므로** 안전하다 — 미매칭·지점 미등록이면 생성을 건너뛰고 화면에 경고만 남긴다.
**30-we는 crawling 테이블(`hottracks_purchase_order*`)에 쓰지 않는다** — 읽기만. 납품 상태는 [배송대기] 버튼이 호출하는 내부 API가 crawling 쪽에서 기록한다.

> **의뢰 #5(쿠팡 판매자배송)과의 차이 요약**
> - #5는 **로젠 송장 발급**이 목적 → 여기(#6)는 **거래명세서 생성**이 목적(의뢰 #3의 `createSupply` 재사용).
> - #5 내부 API 키는 쿠팡 주문번호(단일값) → 여기(#6)는 발주 복합키 `(plorRdpCode, plorDate, plorNum)`.
> - **여러 지점(수불처)이 동시에 발주**할 수 있다. 발주 목록의 각 행 = 한 발주 = 한 지점. 행마다 독립적으로 [거래명세서 생성]/[납품확인]을 누른다.

```sql
    delivered_at          DATETIME(6)  NULL,              -- 핫트랙스 납품확인 완료 (crawling이 기록)
    delivery_mode         VARCHAR(10)  NULL,              -- TMPR(임시저장) / CMPLT(납품확인) (crawling이 기록)
    last_error            VARCHAR(1000) NULL,             -- 납품등록 봇 실패 메시지 (crawling이 기록)
    collected_at          DATETIME(6)  NOT NULL,          -- 마지막 수집 시각

CREATE TABLE hottracks_purchase_order_item (
    order_item_id     BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
    purchase_order_id BIGINT       NOT NULL,              -- hottracks_purchase_order.purchase_order_id (FK)
    barcode           VARCHAR(50)  NULL,                  -- 상품코드(바코드). TradeProduct 완전일치 매칭 키. crawling이 정규화 저장.
    cmdt_id           VARCHAR(30)  NULL,                  -- 핫트랙스 내부 상품ID (참고용)

    sale_unpr         BIGINT       NULL,                  -- 판매가(개당)
    pros_qntt         INT          NULL,                  -- 납품량 (crawling이 납품확인 시 기록, 최초 null)
    match_status      VARCHAR(20)  NULL,                  -- MATCHED / UNMATCHED (crawling 관측용)
    KEY ix_hottracks_poi_order (purchase_order_id)

```

상태 해석:
- `delivered_at IS NULL` = 미납품(작업 대상), `delivered_at IS NOT NULL` = 납품확인 완료.
- `status`로도 판별 가능하나 **화면 필터는 `delivered_at` 기준**을 권장(타임스탬프가 원본).
- item 조인 키는 `purchase_order_id`(=order의 PK). 쿠팡(#5)은 `order_id`로 조인했지만 교보는 **PK로 조인**하니 주의.

> ⚠️ `barcode`는 crawling이 `BarcodeNormalizer`로 **정규화 저장**한다. 30-we의 `TradeProduct.barcode_list`(의뢰 #3 3-2 참조)도 같은 규칙으로 완전일치(=) 매칭해야 한다. 미매칭 시 명세서에서 제외되고 경고를 표시한다(silent failure 방지 — 의뢰 #3 auditBarcodeMatch와 동일 취지).

```php
    $table->timestamp('sms_sent_at')->nullable();           // 발송 안내 문자 전송 시각
```

#### 6-5. 지점(수불처) → 위탁 거래처 매핑 — 기존 기능 재사용, 신규 UI 없음

명세서 생성 시 발주의 지점(`plor_rdp_code`/`plor_rdp_name`)을 30-we의 **위탁 거래처(`TradePartner`, `trade_type=consignment`)로 매핑**해야 한다. 의뢰 #3 3-5와 동일하게 **기존 "거래처 등록" 화면**을 그대로 쓰고, 별도 화면을 만들지 않는다.

- 교보 각 지점을 위탁 거래처로 1개씩 등록하되, **핫트랙스 수불처 코드(`plor_rdp_code`)를 거래처의 식별 필드에 저장**한다. 기존 `TradePartner`에 여유 필드가 없으면 `external_code`(또는 유사) 컬럼 1개만 추가(마이그레이션) 후 거래처 등록 폼에 입력란 추가.
- 명세서 생성 시 `plor_rdp_code`로 `TradePartner`를 역조회해 `partner_id`를 얻는다. **매핑이 없으면 명세서 생성 불가** → 화면에서 "미등록 지점: {지점명}({코드}) — 거래처 등록 필요" 경고.

> ⚠️ 교보 지점 매핑이 빠지면 그 발주는 명세서를 만들 수 없다. 운영에서 발주가 들어오는 교보 지점을 위탁 거래처로 먼저 등록해야 한다(운영 준비 작업, 코드 아님).

#### 6-7. 컨트롤러 (전체 코드 — 신규 `HottracksController`)

```php
<?php // app/Http/Controllers/Admin/HottracksController.php
namespace App\Http\Controllers\Admin;

use App\Http\Controllers\Controller;
use App\Models\HottracksPurchaseOrder;
use App\Models\TradeHottracksSupply;
use App\Models\TradePartner;
use App\Models\TradeProduct;
use App\Models\TradeSupply;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Auth;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Http;
use Illuminate\Support\Facades\Log;

class HottracksController extends Controller
{
    // 교보 발주 목록
    public function purchaseOrderList(Request $request)
    {
        if (!Auth::user()->hasRole(['system_admin', 'idus_admin'])) {
            echo "<script>alert('권한 없는 페이지입니다.');history.back();</script>";
            return;
        }

        $query = HottracksPurchaseOrder::with('items');

        $status = $request->get('status', 'pending'); // pending(기본) | done | all
        if ($status === 'pending') {
            $query = $query->whereNull('delivered_at');
        } elseif ($status === 'done') {
            $query = $query->whereNotNull('delivered_at');
        }

        $order_count = $query->count();
        $orders = $query->orderBy('plor_date', 'asc')->orderBy('plor_num', 'asc')->paginate(40);

        // 생성된 명세서 매칭 (발주키 기준)
        $keys = [];
        foreach ($orders as $o) {
            $keys[] = $o->plor_rdp_code . '|' . $o->plor_date . '|' . $o->plor_num;
        }
        $supplies = TradeHottracksSupply::get()->keyBy(function ($s) {
            return $s->plor_rdp_code . '|' . $s->plor_date . '|' . $s->plor_num;
        });

        return view('admin.hottracks.order_list', [
            'orders' => $orders,
            'order_count' => $order_count,
            'supplies' => $supplies,
            'status' => $status,
        ]);
    }

    // [버튼A] 발주 → 위탁 거래명세서 자동생성 (바코드 매칭, createSupply 재사용)
    public function createSupplyFromOrder(Request $request)
    {
        $user = Auth::user();
        $order = HottracksPurchaseOrder::with('items')
            ->where('plor_rdp_code', $request->get('plor_rdp_code'))
            ->where('plor_date', $request->get('plor_date'))
            ->where('plor_num', $request->get('plor_num'))
            ->first();
        if (!$order) {
            return response()->json(['isSuccess' => false, 'message' => '발주를 찾을 수 없습니다.'], 200);
        }
        if ($order->delivered_at) {
            return response()->json(['isSuccess' => false, 'message' => '이미 납품확인된 발주입니다.'], 200);
        }

        // 1) 지점(수불처) → 위탁 거래처 매핑
        $partner = TradePartner::where('external_code', $order->plor_rdp_code)->first();
        if (!$partner) {
            return response()->json(['isSuccess' => false,
                'message' => '미등록 지점입니다. 거래처 등록 필요: ' . $order->plor_rdp_name . '(' . $order->plor_rdp_code . ')'], 200);
        }

        // 2) 바코드 → TradeProduct 완전일치 매칭 (미매칭은 제외 + 경고)
        //    barcode_list 매칭 규칙은 의뢰 #3 3-2와 동일. crawling은 정규화 저장하므로 동일 규칙으로 매칭.
        $items = [];
        $unmatched = [];
        foreach ($order->items as $it) {
            $product = TradeProduct::whereHas('barcodes', function ($q) use ($it) {
                $q->where('barcode', $it->barcode);   // 의뢰 #3 3-2의 barcode_list 완전일치와 동일
            })->first();
            if (!$product) {
                $unmatched[] = $it->barcode . ' (' . $it->product_name . ')';
                continue;
            }
            $items[] = [
                'product_id'   => $product->id,
                'product_name' => $it->product_name,
                'barcode'      => $it->barcode,
                'quantity'     => (int) $it->plor_qntt,   // 발주량 = 기본 납품량 (화면에서 수정 가능)
                'unit_price'   => (int) $it->sale_unpr,
                'sale_price'   => (int) $it->sale_unpr,
            ];
        }
        if (empty($items)) {
            return response()->json(['isSuccess' => false,
                'message' => '매칭된 상품이 없습니다. 미매칭: ' . implode(', ', $unmatched)], 200);
        }

        // 3) 위탁 거래명세서 생성 (의뢰 #3의 SupplyService::createSupply 재사용)
        try {
            $supply = DB::transaction(function () use ($user, $partner, $items, $order) {
                $s = app(\App\Services\SupplyService::class)->createSupply($user, [
                    'partner_id'    => $partner->id,
                    'supply_type'   => TradeSupply::SUPPLY_TYPE_CONSIGNMENT,
                    'supply_date'   => now()->toDateString(),
                    'delivery_date' => now()->toDateString(),
                    'items'         => $items,
                ]);

                TradeHottracksSupply::updateOrCreate(
                    ['plor_rdp_code' => $order->plor_rdp_code,
                     'plor_date' => $order->plor_date,
                     'plor_num' => $order->plor_num],
                    ['user_id' => $user->id,
                     'trade_supply_id' => $s->id,
                     'supply_created_at' => now(),
                     'delivered_at' => null]   // 재생성 시 납품상태 초기화
                );
                return $s;
            });
        } catch (\Exception $e) {
            return response()->json(['isSuccess' => false, 'message' => '명세서 생성 실패: ' . $e->getMessage()], 200);
        }

        return response()->json([
            'isSuccess'  => true,
            'supply_id'  => $supply->id,
            'unmatched'  => $unmatched,   // 있으면 UI에 "일부 미매칭" 경고
            'pdf_url'    => route('admin::...trade::downloadSupplyPdf', ['id' => $supply->id]), // 현행 PDF 라우트명으로 교체
        ], 200);
    }

    // [버튼B] 납품확인 (crawling 내부 API 호출 — 핫트랙스 납품확인 페이지에 수량 입력)
    public function deliver(Request $request)
    {
        $order = HottracksPurchaseOrder::with('items')
            ->where('plor_rdp_code', $request->get('plor_rdp_code'))
            ->where('plor_date', $request->get('plor_date'))
            ->where('plor_num', $request->get('plor_num'))
            ->first();
        if (!$order) {
            return response()->json(['error' => '발주를 찾을 수 없습니다'], 404);
        }
        if ($order->delivered_at) {
            return response()->json(['error' => '이미 납품확인된 발주입니다'], 409);
        }

        // 생성된 명세서의 확정 수량을 items로 전달 (없으면 발주량 그대로)
        $supplyLink = TradeHottracksSupply::where('plor_rdp_code', $order->plor_rdp_code)
            ->where('plor_date', $order->plor_date)
            ->where('plor_num', $order->plor_num)->first();
        if (!$supplyLink) {
            return response()->json(['error' => '거래명세서를 먼저 생성해주세요'], 400);
        }

        // 명세서 품목 → {barcode, qty}. 명세서에서 수량을 수정했다면 그 값이 반영된다.
        $supply = TradeSupply::with('items')->find($supplyLink->trade_supply_id);
        $items = [];
        foreach ($supply->items as $si) {
            $bc = $si->barcode;   // 명세서 아이템에 바코드 보존 필요(createSupply items에 barcode 전달함)
            if (!empty($bc) && (int) $si->quantity > 0) {
                $items[] = ['barcode' => $bc, 'qty' => (int) $si->quantity];
            }
        }
        if (empty($items)) {
            return response()->json(['error' => '납품할 수량이 없습니다'], 400);
        }

        $response = Http::withHeaders([
            'X-Internal-Token' => config('services.crawling.internal_token'),
        ])->timeout(120)->post(   // Selenium 봇 실행이라 타임아웃 여유
            config('services.crawling.base_url') . '/internal/hottracks/orders/deliver',
            [
                'plorRdpCode' => $order->plor_rdp_code,
                'plorDate'    => $order->plor_date,
                'plorNum'     => $order->plor_num,
                'items'       => $items,
                'mode'        => 'CMPLT',   // 납품확인. crawling 서버 안전플래그가 false면 임시저장으로 강등됨(응답 confirmed=false)
            ]
        );

        if (!$response->successful()) {
            $body = $response->json();
            $message = isset($body['message']) ? $body['message'] : $response->body();
            Log::error('교보 납품확인 실패', ['plorNum' => $order->plor_num, 'status' => $response->status(), 'body' => $body]);
            return response()->json(['error' => '납품확인 실패: ' . $message], $response->status());
        }

        $result = $response->json(); // {plorNum, confirmed, mode, filledRows, unmatched, message}
        if (!empty($result['confirmed'])) {
            $supplyLink->update(['delivered_at' => now()]);
        }
        return response()->json($result);
    }
}
```

> `SupplyService::createSupply`는 의뢰 #3 3-4(1)에서 추출을 요청한 그 서비스다. 의뢰 #3을 먼저 구현했다면 그대로 재사용하면 되고, 아직이면 이번에 함께 추출한다. `createSupply` items 스펙에 `barcode`가 포함되며, `TradeSupplyItem`에 barcode를 보존해야 [버튼B]에서 바코드를 다시 얻을 수 있다(보존 안 되면 deliver에서 명세서 대신 원 발주 item의 바코드를 사용).

crawling 수집(매시 40분) 직후 신규 발주를 감지해 **가거래명세서를 자동 생성**한다. Kernel 등록:

1. 기존 6-7 `deliver`대로 crawling 내부 API 호출(6-8). **실패하면 여기서 중단** — 송장·문자 안 나감.


#### 6-8. crawling 내부 API 계약 (구현 완료 — [배송대기(납품확인)] 처리 ①에서 호출)

```
POST {CRAWLING_BASE_URL}/internal/hottracks/orders/deliver
Header: X-Internal-Token: {토큰}
Body:   {
          "plorRdpCode": "527",
          "plorDate": "20260824",
          "plorNum": "00022",
          "items": [{"barcode": "8809...", "qty": 3}, ...],
          "mode": "CMPLT"        // TMPR(임시저장) | CMPLT(납품확인). 생략 시 CMPLT.
        }
```

동작: 발주키의 **핫트랙스 납품확인 페이지(prdt1012)에 상품별 납품량을 바코드로 매칭 입력**하고, `mode`에 따라 임시저장/납품확인을 수행한다. bsight 발주 행에 상태를 기록한다. **멱등**: `delivered_at`이 이미 있으면 409로 거부한다.

> **안전장치:** crawling 서버 설정 `hottracks.delivery.allow-final-confirm`(기본 `false`)이 `false`면, `mode=CMPLT`로 보내도 **임시저장(TMPR)으로 강등**된다. 이 경우 응답 `confirmed=false`, `mode="TMPR"`로 돌아온다. 즉 **운영 전환(true) 전까지는 [납품확인]을 눌러도 핫트랙스 최종 납품확인이 되지 않고 임시저장까지만** 된다. UI는 `confirmed` 값을 보고 "임시저장됨(최종확인 대기)" / "납품확인 완료"를 구분 표시할 것.

성공 `200`:
```json
{"plorNum": "00022", "confirmed": true, "mode": "CMPLT",
 "filledRows": 9, "unmatched": [],
 "message": "납품확인 완료"}
```
- `confirmed`: 최종 납품확인까지 됐으면 `true`, 임시저장까지면 `false`.
- `filledRows`: 납품확인 페이지에서 실제 수량을 채운 상품 행 수.
- `unmatched`: 납품확인 페이지에서 바코드로 행을 못 찾은 항목(있으면 UI 경고).

| status | body.error | 의미 / 30-we 처리 |
|---|---|---|
| 401 | unauthorized | 토큰 확인 |
| 404 | order_not_found | crawling에 없는 발주키 |
| 409 | invalid_state | 이미 납품확인된 발주 — 메시지 그대로 표시 |
| 400 | bad_request | 파라미터/항목 누락 (바코드·수량 확인) |
| 502 | crawler_error | 핫트랙스 봇(Selenium) 오류 — 메시지 표시 후 재시도 안내 |

- 봇 실행 시간이 길 수 있으므로 30-we HTTP 타임아웃은 **120초 이상** 권장(6-7 컨트롤러 참조).

### 의뢰 #7 — 위탁 거래처 발주 자동 수신 + AI 거래명세서 작성 (발주 수신함)

**상태: 확정 (일부 결정 필요 항목 §7-11)**
**예외 유형** (의뢰 #3·#5·#6과 동일): 30-we가 읽기 전용이 아니라 **쓰기·액션까지 수행**한다.
**⚠️ 이번 의뢰는 crawling이 전혀 관여하지 않는다** — bsight 테이블도, 내부 API도 없다. 구성 요소는 (a) **안드로이드 수신기 앱**(업무폰)과 (b) **30-we 자체 기능**(수신 API + 발주 수신함 + AI 파싱 + 확정 UX) 두 가지다.

#### 7-1. 배경과 전체 그림

위탁 거래처들은 각자 편한 채널(문자, 카카오톡, 메일)로 각자 양식(자유 텍스트, 사진, 엑셀)의 발주를 **업무폰**으로 보낸다. 현재는 사람이 업무폰과 30-we를 오가며 발주 내용을 수기로 거래명세서에 입력한다. 목표:

```
[업무폰]   발주 도착 (문자/카톡/메일 알림)
[수신앱]   알림 수신기(NotificationListener)가 감지 → 발신자·본문·첨부를 30-we로 자동 전송
[30-we]    [발주 수신함]에 원본 저장
            → AI가 자동 파싱: 거래처 추천 + 품목·수량·단가 초안 (미확정)
            → 사용자: 수신함 화면에서 원본과 초안을 나란히 보며
              항목마다 "맞으면 Enter=확정 / 틀리면 수정 후 Enter"
            → 전체 확정 → 위탁 거래명세서(consignment) 생성
            → (기존 기능) 명세서 출력 → 포장 → 로젠 송장 → 담당자 문자
```

핵심 원칙 — **다른 의뢰와 달리 자동 생성이 아니다.** 데이터가 정형으로 들어오지 않으므로:
- AI는 **초안(사전 세팅)만** 만든다. 확정 전에는 `TradeSupply`를 생성하지 않는다.
- 거래처를 포함한 **모든 값의 확정은 사람**이 한다 (항목별 Enter 확정 UX, §7-8).
- 기존 GPT 파싱(`TradeController::parseExcelWithGpt`, 약 3545행)과 거래처별 `gpt_prompt`를 재활용한다.

#### 7-2. Part A — 안드로이드 수신기 앱 (업무폰)

기존 `android-live/`(Kotlin, `com.thirtywe.live`) 프로젝트 구조를 참고해 **별도 앱**으로 만든다 (예: `android-order-receiver/`, 패키지 `com.thirtywe.orderreceiver`). 알림 수신부는 웨어러블 프로젝트에서 쓰는 이벤트 수신기 구현을 재활용한다 (구현 소스는 별도 전달).

**A-1. 알림 수신 (NotificationListenerService)**

```kotlin
class OrderNotificationListener : NotificationListenerService() {
    // 대상 앱 화이트리스트 — 설정 화면에서 토글 (기본값 아래)
    private val targetPackages = setOf(
        "com.kakao.talk",                       // 카카오톡
        "com.samsung.android.messaging",        // 삼성 메시지 (SMS)
        "com.google.android.apps.messaging",    // 구글 메시지 (SMS)
        "com.google.android.gm",                // Gmail
    )

    override fun onNotificationPosted(sbn: StatusBarNotification) {
        if (sbn.packageName !in targetPackages) return   // ⚠️ 화이트리스트 필수 (개인정보 — §7-11)
        val extras = sbn.notification.extras
        val sender = extras.getCharSequence(Notification.EXTRA_TITLE)?.toString() ?: return
        val body = extras.getCharSequence(Notification.EXTRA_BIG_TEXT)?.toString()
            ?: extras.getCharSequence(Notification.EXTRA_TEXT)?.toString() ?: return
        UploadQueue.enqueue(
            IngestPayload(
                sourceChannel = channelOf(sbn.packageName),  // kakao | sms | mail
                sender = sender,
                body = body,
                receivedAt = sbn.postTime,
                dedupeKey = "${sbn.packageName}|${sender}|${body.hashCode()}|${sbn.postTime / 60000}",
            )
        )
    }
}
```

- 그룹 요약 알림(`FLAG_GROUP_SUMMARY`)은 건너뛴다 (개별 메시지 알림만 전송).
- 같은 대화의 연속 메시지는 각각 한 건씩 올라간다 — 서버에서 묶지 않고 수신함에 개별 행으로 둔다 (사용자가 화면에서 함께 보고 처리).

```php
// 반환: ['partner_suggestion' => ['partner_id'=>N|null, 'confidence'=>'high|low', 'reason'=>...],
```

기존 대비 확장 2가지:

2. **다중 이미지**: 공유 인텐트로 사진 여러 장이 온 건은 이미지 배열로 전달.

**파싱 시점 — 수신 후 자동 (스케줄 커맨드).** ingest 응답을 지연시키지 않도록 동기 파싱하지 않고, 기존 Kernel 패턴(`budget:generate-scheduled`)대로 커맨드를 등록한다:


`order-inbox:parse`: `status='NEW'` 건을 오래된 순으로 최대 N건 파싱 → `parsed_json`·`matched_partner_id`·`parsed_at` 기록, `status='PARSED'`. OpenAI 오류 시 상태 유지(다음 회차 재시도), 3회 실패하면 `parsed_json`에 오류 표기 후 PARSED로 넘겨 사람이 수기 입력하게 한다.

1. **첨부 원본 확보 (가장 중요한 한계).** 안드로이드 알림에는 본문 미리보기만 담긴다 — 카톡 사진·메일 첨부 엑셀의 **원본은 알림으로 오지 않는다.** 1차 릴리즈 권장 범위: **알림 텍스트 자동 수신 + 공유 인텐트로 첨부 수동 업로드**(폰에서 "공유" 2탭). 이후 확장 옵션: 메일은 서버 측 IMAP 수집(전용 메일함), 카톡 사진은 저장 폴더(MediaStore) 감시. 어디까지 갈지 결정 필요.

### 의뢰 #8 — 쿠팡 로켓그로스 입고 신청 자동화 (신청 화면 + 로젠 송장 자동 발급 + RPA 연계)

**상태: 확정** — crawling 서버(테이블·내부 API 4종·에이전트 API·추적 배치) **구현·배포 완료(2026-08-26)**. 에이전트도 핵심 로직 구현 완료(WING 주소 동기화는 실계정 검증까지 완료 — 회송지 드롭다운 데이터가 이미 적재돼 있음). §8-7 API는 운영 서버에서 호출 가능한 상태이므로 **30-we 작업을 바로 시작할 수 있다.** 에이전트 설치 파일 전달 시 "전달됨"으로 변경.
**예외 유형** (의뢰 #3·#5·#6과 동일): 30-we가 읽기 전용이 아니라 **액션(crawling API 호출, 로젠 송장 발급)까지 수행**한다.

#### 8-1. 배경과 전체 그림

쿠팡은 로켓그로스 **입고 신청 API를 제공하지 않는다** (검증 완료 — 파스토·아르고 등 3PL도 전부 미연동). 그래서 담당자 PC에 상주하는 **RPA 에이전트**(crawling 팀이 개발·배포하는 별도 프로그램)가 쿠팡 WING 화면을 자동 조작해 입고를 제출한다. 2026-08-25 실계정 PoC로 전 과정(제출→정보 회수→취소) 검증 완료.

30-we는 **사람이 판단·개입하는 화면**을 맡는다: 입고 신청 화면(추천 프리필), 신청 내역/상세, 송장 발급 버튼, 에이전트 다운로드 페이지.

```
[crawling]   RG 재고/판매 수집 → 입고 제안 생성(의뢰 #2) → 슬랙 알림 (30-we 신청 화면 링크 포함)
[30-we]      ① 입고 신청 화면: 제안 상품·권장수량 프리필 → 상품 추가/삭제·수량·박스 수 입력
             → [입고 신청하기] = crawling 내부 API 호출(계획 생성) + rginbound:// 프로토콜 호출
[에이전트]    ② 담당자 PC에서 WING 입고생성 자동 입력 → 제출 → 입고ID·물류센터·도착예정일·문서(PDF) 회수 → crawling에 보고
[30-we]      ③ 신청 상세 화면: 상태·WING 정보 표시, 문서 CDN URL 링크(새 탭 → 인쇄), [송장 발급] 버튼
             → 로젠 발급 (수하인 = 쿠팡이 배정한 물류센터 주소, 박스 수만큼) → 송장번호를 crawling에 전달
[에이전트]    ④ WING 해당 입고 건에 송장번호 자동 등록
[crawling]   ⑤ RG 재고 API로 입고 반영 감지 → 계획 상태 COMPLETED/MISMATCH 갱신 + 슬랙 알림
```

- **30-we는 crawling 테이블에 직접 쓰지 않는다.** 쓰기가 필요한 모든 동작(계획 생성, 송장 전달, 설정 저장)은 crawling 내부 API 호출로 수행하고, 화면 표시는 패턴 A(DB 조회)로 한다.
- `rginbound://` 프로토콜은 에이전트가 설치된 PC에서만 동작한다. 미설치 PC/모바일에서 신청해도 **에이전트가 10분 주기로 crawling에 폴링**하므로 자동 처리된다 (프로토콜은 즉시 실행용 최적화일 뿐).
- 에이전트 설치 파일(맥 .dmg / 윈도우 .exe)은 crawling 팀이 빌드해 전달 → 30-we는 다운로드 페이지에 배치만 한다.

```php
    if (!Auth::user()->hasRole(['system_admin', 'idus_admin'])) {

// [의뢰 #8] 입고 신청 실행 (crawling 내부 API 호출 → 계획 생성)
public function inboundRequestSubmit(Request $request)
{
    $items = $request->input('items'); // [{vendorItemId, quantity}, ...]
    $boxCount = (int) $request->input('boxCount');

    if (empty($items) || $boxCount < 1) {
        return response()->json(['error' => '상품과 박스 수를 입력해주세요'], 400);
    }

    $response = Http::withHeaders([
        'X-Internal-Token' => config('services.crawling.internal_token'),
    ])->timeout(30)->post(
        config('services.crawling.base_url') . '/internal/coupang/rg-inbound/plans',
        [
            'items' => $items,
            'boxCount' => $boxCount,
            'requestedBy' => Auth::user()->name,
        ]
    );

    if (!$response->successful()) {
        $body = $response->json();
        $message = isset($body['message']) ? $body['message'] : $response->body();
        Log::error('입고 계획 생성 실패', ['status' => $response->status(), 'body' => $body]);

// [의뢰 #8] 로젠 송장 발급 (박스 수만큼, 수하인 = 배정 FC) + crawling 전달
public function issueInboundWaybills(Request $request, $planId)
{
    $plan = CoupangInboundPlan::with('items')->findOrFail($planId);

    if (!in_array($plan->status, ['SUBMITTED', 'INVOICE_ISSUED'])) { // INVOICE_ISSUED = 재발급 허용
        return response()->json(['error' => '송장 발급 가능 상태가 아닙니다: ' . $plan->status], 409);
    }
    $fc = CoupangFulfillmentCenter::where('fc_name', $plan->fulfillment_center)->first();
    if (!$fc) {
        return response()->json(['error' => 'FC 주소 미등록: ' . $plan->fulfillment_center . ' (관리자에게 문의)'], 422);
    }

    $firstItem = $plan->items->first();
    $itemLabel = '로켓그로스 입고 ' . ($plan->wing_inbound_id ?: $planId);

    $service = app(\App\Services\WaybillIssuanceService::class); // 의뢰 #5에서 추출한 서비스 재사용
    $slips = [];
    $invoices = [];
    for ($boxNo = 1; $boxNo <= $plan->box_count; $boxNo++) {
        try {
            $result = $service->issue(
                $fc->receiver_name,
                $fc->phone ?: '0000000000',
                $fc->address,
                $itemLabel . ' (' . $boxNo . '/' . $plan->box_count . ')',
                'RG' . $planId . '-' . $boxNo
            );
        } catch (\Exception $e) {
            return response()->json(['error' => '로젠 발급 실패 (박스 ' . $boxNo . '): ' . $e->getMessage()], 502);
        }

        TradeRgInboundWaybill::updateOrCreate(
            ['plan_id' => $planId, 'box_no' => $boxNo],
            ['tracking_number' => $result['tracking_number'], 'issued_at' => now()]
        );
        $slips[] = $result['slip'];
        $invoices[] = ['boxNo' => $boxNo, 'trackingNumber' => $result['tracking_number']];
    }

    // crawling에 송장 전달 → 에이전트가 WING에 등록
    $response = Http::withHeaders([
        'X-Internal-Token' => config('services.crawling.internal_token'),
    ])->timeout(30)->post(
        config('services.crawling.base_url') . '/internal/coupang/rg-inbound/plans/' . $planId . '/invoices',
        ['invoices' => $invoices]
    );

    if (!$response->successful()) {
        // 발급은 성공했으므로 실패해도 송장은 유지 — 재시도 안내만
        Log::error('입고 송장 전달 실패', ['planId' => $planId, 'status' => $response->status()]);
        return response()->json([
            'warning' => '송장 발급은 완료됐으나 crawling 전달에 실패했습니다. [송장 발급]을 다시 눌러 재전달하세요.',
            'slips' => $slips,
        ]);
    }

    return response()->json(['slips' => $slips]); // 라벨 출력 팝업용 (기존 logen_print_js 재사용)
}
```

#### 8-7. crawling 내부 API 계약 (crawling이 제공 — 30-we가 호출)

**① 입고 계획 생성** (신청 버튼):

```
POST {CRAWLING_BASE_URL}/internal/coupang/rg-inbound/plans
Header: X-Internal-Token: {토큰}
Body:   {"boxCount": 2, "requestedBy": "홍길동",
         "items": [{"vendorItemId": 95296581965, "quantity": 60},
                   {"vendorItemId": 95297205499, "quantity": 40}]}
```

성공 `200`: `{"planId": 123}` — 동시에 해당 SKU의 `coupang_restock_suggestion.status`가 `REQUESTED`로 갱신됨(의뢰 #2 화면에 반영).

| status | body.error | 의미 / 30-we 처리 |
|---|---|---|
| 401 | unauthorized | 토큰 확인 |
| 400 | bad_request | items 비어있음 / boxCount < 1 |
| 409 | return_address_not_set | 회송지 미설정 — "회송지를 먼저 설정해주세요" 표시 |
| 409 | duplicate_in_progress | 이미 진행 중 계획에 포함된 SKU — 메시지 그대로 표시 |

**② 송장 전달** (송장 발급 버튼 — 발급 후 호출):

```
POST {CRAWLING_BASE_URL}/internal/coupang/rg-inbound/plans/{planId}/invoices
Body:   {"invoices": [{"boxNo": 1, "trackingNumber": "12345678901"},
                      {"boxNo": 2, "trackingNumber": "12345678902"}]}
```

성공 `200`: `{"planId": 123, "status": "INVOICE_ISSUED"}` — crawling이 에이전트 작업을 생성하고, 에이전트가 WING 등록 완료 시 상태를 `INVOICE_REGISTERED`로 갱신. 재호출(재발급) 시 기존 송장을 덮어쓰고 재등록한다(멱등).

| status | body.error | 의미 |
|---|---|---|
| 404 | plan_not_found | 계획 없음 |
| 409 | invalid_state | SUBMITTED/INVOICE_ISSUED 상태가 아님 |
| 400 | bad_request | invoices 개수가 box_count와 불일치 |

**③ 회송지 설정 저장:**

```
PUT {CRAWLING_BASE_URL}/internal/coupang/rg-inbound/settings
Body:   {"returnAddress": "경기도 광주시 문형산길 246-9 B 01호"}
```

성공 `200`: `{"saved": true}`. `422 address_not_in_wing`: 전달한 주소가 `coupang_wing_address` 목록에 없음(주소는 반드시 드롭다운에서 선택 — 자유 입력 금지).

**④ 문서(바코드/부착문서) — API 아님, CDN URL 직링크:**

에이전트가 WING에서 PDF 2종을 내려받아 **사내 CDN(refrigerator, 교보 발주 원본과 동일)**에 올리고, URL을 plan 행에 저장한다 (`barcode_pdf_url` / `attach_pdf_url` — 제출 완료 슬랙 알림에도 포함됨). 30-we는 이 URL을 `target="_blank"`로 직접 링크만 하면 된다. NULL이면 아직 회수 전이므로 버튼 비활성.

#### 8-10. 제약 / 주의

- **WING 제출·송장 등록의 실행 주체는 에이전트다.** 30-we의 신청/송장 버튼은 "crawling에 기록"까지만 책임지며, 화면에는 반드시 상태 기반으로 표시한다 (버튼을 눌렀다고 제출된 것이 아님 — status가 SUBMITTED가 되어야 제출된 것).
- `rginbound://` 프로토콜 호출은 실패해도 무해하다 (브라우저가 "알 수 없는 프로토콜"로 무시 → 에이전트 폴링이 처리). 별도 오류 처리 불필요.
- 송장 발급 시점: 실물 포장 완료 후 사용자가 누른다 (모드 A — 사전 발급 아님). 박스 수가 신청 때와 달라졌으면 재발급 흐름 사용.
- `coupang_restock_suggestion.status` 갱신(REQUESTED/COMPLETED)은 전부 crawling이 수행 — 의뢰 #2 화면은 수정 불필요.
- PHP 7.3 문법 준수 (arrow function 사용 금지).
